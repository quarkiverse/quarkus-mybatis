= Quarkus - Using MyBatis

:extension-status: preview

This guide demonstrates how your Quarkus application can use link:{mybatis-root-url}[MyBatis] to support custom SQL, stored procedures and advanced mappings.

== Prerequisites

To complete this guide, you need:

* less than 15 minutes
* an IDE
* JDK 17+ installed with `JAVA_HOME` configured appropriately
* Apache Maven
* A running Mysql Database server
* GraalVM, or Docker, installed if you want to run in native mode.

== Architecture

The application built in this guide is quite simple: the user can get, add and remove a record through the RESTful API by using the MyBatis Mapper.


== Solution

We recommend that you follow the instructions in the next sections and create the application step by step.

== Creating the Maven Project

First, we need a new project. Create a new project with the following command:

[source, bash, subs=attributes+]
----
mvn io.quarkus:quarkus-maven-plugin:{quarkus-version}:create \
    -DprojectGroupId=org.acme \
    -DprojectArtifactId=mybatis-quickstart \
    -Dextensions="resteasy-jackson,jdbc-mysql,io.quarkiverse.mybatis:quarkus-mybatis:{quarkus-mybatis-version}" \
    -DnoExamples
cd mybatis-quickstart
----

[TIP]
====
After creating the project, use its Maven wrapper (`./mvnw`) for the remaining commands.
====

This command generates a Maven project, with its pom.xml importing the quarkus-mybatis extension.

If you already have your Quarkus project configured, you can add the `quarkus-mybatis` extension
to your project by adding the following dependency in your `pom.xml`:

[source, subs=attributes+]
----
<dependency>
    <groupId>io.quarkiverse.mybatis</groupId>
    <artifactId>quarkus-mybatis</artifactId>
    <version>{quarkus-mybatis-version}</version>
</dependency>
----

== Creating the User POJO
We are going to create a `User` POJO to access to the data in the backend mysql server.
Create the `src/main/java/org/acme/mybatis/User.java` file, with the following content:

[source, java]
----
package org.acme.mybatis;

public class User {
    private Integer id;
    private String name;

    public Integer getId() {
        return id;
    }

    public void setId(Integer id) {
        this.id = id;
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }
}
----

== Creating the User Mapper
We are going to create a `UserMapper` class which will use the MyBatis annotations to inject the SQL.
Create the `src/main/java/org/acme/mybatis/UserMapper.java` file, with the following content:

[source, java]
----
package org.acme.mybatis;

import org.apache.ibatis.annotations.Delete;
import org.apache.ibatis.annotations.Insert;
import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Param;
import org.apache.ibatis.annotations.Select;

@Mapper
public interface UserMapper {

    @Select("SELECT * FROM USERS WHERE id = #{id}")
    User getUser(Integer id); // <1>

    @Insert("INSERT INTO USERS (id, name) VALUES (#{id}, #{name})")
    Integer createUser(@Param("id") Integer id, @Param("name") String name); // <2>

    @Delete("DELETE FROM USERS WHERE id = #{id}")
    Integer removeUser(Integer id); // <3>
}
----

1. Get a user from the database.
2. Insert a user into the database. We should use the `@Param` to bind the parameters.
3. Delete a user from the databse.

== Creating the MyBatisResource to handle the requests
We are going to create a `MyBatisResource` class which will handle all the requests to create, query or remove the data
from the database.

[source, java]
----
package org.acme.mybatis;

import jakarta.inject.Inject;
import jakarta.ws.rs.Consumes;
import jakarta.ws.rs.DELETE;
import jakarta.ws.rs.FormParam;
import jakarta.ws.rs.GET;
import jakarta.ws.rs.POST;
import jakarta.ws.rs.Path;
import jakarta.ws.rs.PathParam;
import jakarta.ws.rs.Produces;
import jakarta.ws.rs.core.MediaType;

@Path("/mybatis")
public class MyBatisResource {

    @Inject
    UserMapper userMapper; // <1>

    @Path("/user/{id}")
    @GET
    @Produces(MediaType.APPLICATION_JSON)
    public User getUser(@PathParam("id") Integer id) {
        return userMapper.getUser(id);
    }

    @Path("/user")
    @POST
    @Produces(MediaType.TEXT_PLAIN)
    @Consumes(MediaType.APPLICATION_FORM_URLENCODED)
    public Integer createUser(@FormParam("id") Integer id, @FormParam("name") String name) {
        return userMapper.createUser(id, name);
    }

    @Path("/user/{id}")
    @DELETE
    @Produces(MediaType.TEXT_PLAIN)
    public Integer removeUser(@PathParam("id") Integer id) {
        return userMapper.removeUser(id);
    }
}
----
1. It uses the UserMapper which should be injected by the Quarkus to access the database.

== Configure the properties

We need to config the datasource used to connect to the database and the mybatis will choose the default one. Also you
can use ```quarkus.mybatis.datasource``` for the specific database.

[source]
----
quarkus.datasource.db-kind=mysql
quarkus.datasource.username=<db user>

quarkus.datasource.jdbc.url=jdbc:mysql://localhost/test  #<1>
quarkus.mybatis.initial-sql=insert.sql  #<2>
----

1. The datasource used by the mybatis to connect the database.
2. The SQL file which should be executed just after the application is started.

We could keep the following content in the `insert.sql` to add some data:
[source, sql]
----
DROP TABLE IF EXISTS USERS;

CREATE TABLE USERS (
    id integer not null primary key,
    name varchar(80) not null
);

INSERT INTO USERS (id, name) values(1, 'Test User1');
INSERT INTO USERS (id, name) values(2, 'Test User2');
INSERT INTO USERS (id, name) values(3, 'Test User3');
----

== Running with the JVM mode
At first, you should make sure the Mysql Server is running and the `test` database has been created.
Then, you just need to run:

[source, shell]
----
./mvnw compile quarkus:dev
----

You can get the user by using the following command:

[source, shell]
----
curl http://localhost:8080/mybatis/user/1
----

Or create a new user:

[source, shell]
----
curl -X POST http://localhost:8080/mybatis/user -d 'id=4&name=test'
----

Or remove a user:

[source, shell]
----
curl -X DELETE http://localhost:8080/mybatis/user/1
----

=== Second level cache in native mode
The default read / write second level cache (enabled with `@CacheNamespace` or `<cache/>`) stores query results using Java serialization.
For mappers that use a read / write cache (`@CacheNamespace`, `@CacheNamespaceRef`, or `<cache/>` / `<cache-ref/>` in the mapper XML),
the extension registers the result types of the mapper interface methods (including the type arguments of generic base mappers),
the types reachable from their fields, and common JDK value types, for serialization automatically.

Types that cannot be discovered this way, such as JDK types not covered by the automatic registration, must be registered manually:

[source,java]
----
@RegisterForReflection(serialization = true)
public class User implements Serializable {
    // ...
}
----

== Support for multiple data sources
You can choose a specific data source for MyBatis mapper using the annotation `@MapperDataSource`.
Query in the next example will be running against data source with name `user`.
If there is no such annotation on the mapper, the default data source will be used.

[source, java]
----
@Mapper
@MapperDataSource("user")
public interface UserMapper {
  @Select("SELECT * FROM USERS WHERE id = #{id}")
  User getUser(Integer id);
}
----

== CDI integration
Injects default session factory:

[source, java]
----
@Inject
SqlSessionFactory sqlSessionFactory;
----

Injects session factory for data source `user`:

[source, java]
----
@Named("user")
SqlSessionFactory sqlSessionFactory;
----

== Transactions and session cleanup

To group mapper calls into one JTA transaction, use the `MANAGED` transaction factory
(the default), a datasource that participates in JTA, and a CDI method annotated with `@Transactional`.

[source, properties]
----
quarkus.mybatis.transaction-factory=MANAGED
quarkus.datasource.jdbc.transactions=enabled
----

For example, this service uses the `UserMapper` defined above to replace a user within one transaction:

[source, java]
----
package org.acme.mybatis;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;
import jakarta.transaction.Transactional;

@ApplicationScoped
public class UserService {
    @Inject
    UserMapper userMapper;

    @Transactional
    public void replaceUser(Integer id, String name) {
        userMapper.removeUser(id);
        userMapper.createUser(id, name);
    }
}
----

JTA controls JDBC commit and rollback. If the insert throws a runtime exception that leaves this method,
the earlier delete is rolled back too. When using XML configuration, select `MANAGED` in the XML
`transactionManager` element as shown below.

=== Commit, rollback and failures

With `MANAGED` and an active JTA transaction, successful mapper calls clear the first-level cache
and flush BATCH statements before returning, but do not commit the JDBC transaction individually.
A caught mapper exception does not by itself mark JTA rollback-only; earlier successful writes can
still commit. The database or a transactional interceptor can independently require rollback.
If failed work cannot be discarded, or session initialization fails after it could have executed SQL,
the facade requests rollback-only. Cleanup failures are attached to the original exception.

Other transaction factories retain per-call MyBatis commit behavior. In particular, `JDBC` with a
datasource that does not enlist in JTA commits successful calls independently; an outer JTA rollback
cannot undo those commits. Outside JTA, the facade completes and closes each MyBatis session before
returning. Use `MANAGED` with a JTA-enabled datasource for the transaction semantics described here.

=== Second-level cache behavior and limits

For managed JTA sessions, eligible second-level cache results are published only after a successful
JTA commit. Potential writes invalidate affected cache regions before executing SQL and prevent
stale publication until transaction completion. Effects that cannot be isolated to one region
invalidate caches across the configuration. A rollback can therefore cause extra cache misses.

Rollback, timeout and unknown transaction outcomes discard pending results. An unknown outcome
also triggers conservative invalidation when the session may have affected database state;
known pure reads need not clear unrelated caches. Cache-provider or cleanup failures can also cause
conservative invalidation. Cache publication is not an XA resource and cannot undo an already committed database transaction.

The current managed cache implementation supports leaf `selectOne` and `selectList` queries whose
rows contain only nulls, strings or primitive wrappers; `selectList` must return a standard `ArrayList`.
DTOs, custom collections, nested-query results, cursors and result-handler calls do not populate
the second-level cache. Such mappings still return their normal results. Other eligible queries
in the same transaction can remain cacheable.

Managed cursor iteration uses the creating session's cache context and bypasses second-level cache
lookups for nested queries. Within the originating JTA transaction, lazy getters running outside a
managed facade scope also bypass that cache, including inside an immediate facade's callback.
Bypassing the second-level cache does not disable MyBatis's first-level cache or change database isolation.
Immediate calls also bypass second-level caches for nested mappings that span cache regions or include uncached statements.

With caching enabled, calling `TransactionalSqlSession.getConnection()` in a managed JTA session
invalidates the configuration's caches before returning the connection, keeps invalidation protection
until transaction completion, and disables publication from that session. JDBC writes through
connections obtained independently of the facade are not tracked.

Coordination covers calls through `TransactionalSqlSession` sharing one configuration in one process.
It does not provide cross-node consistency or coordinate direct `SqlSessionFactory` sessions and external writers.
Managed facades in the same JTA transaction share the cache-version boundary established by the first facade;
a database snapshot established before any facade participates is outside this boundary.

MyBatis `BlockingCache` (`blocking=true`) is rejected for managed JTA sessions when second-level
caching is enabled, even if the current statement does not use that cache. Set `blocking=false`
for all caches in the configuration or disable second-level caching. This rejection does not itself
mark JTA rollback-only. Non-JTA calls continue to support blocking caches.

For custom configurations and runtime mapper registration, see xref:advanced-configuration.adoc[Advanced configuration].

=== Cursors and resource cleanup

Consume and close cursors within the transaction that created them, using try-with-resources.
With `REUSE`, ordinary mapper calls retain statement reuse within the call and release statements
at the call boundary. Open cursors retain their own statements across mapper calls and use the
same JDBC connection. Intervening facade calls clear the associated local caches so later nested
cursor queries can observe writes made in the transaction.

While the originating managed JTA session is active, lazy queries on the result's creating thread
participate in its lifecycle protection. Outside an active mapper call or cursor read on that session,
they use a short-lived `SIMPLE` executor sharing its JDBC connection. Query cleanup closes the
statements without closing an open cursor or the connection.

Lazy loading on another thread, or after the originating session completes, follows MyBatis's
independent-executor path and is outside the originating session's lifecycle protection.

Session resources are cleaned up on commit, rollback and timeout. Cleanup waits for an active
facade call, protected lazy query, cursor read or cursor close to finish before closing the session.
A JTA timeout alone does not guarantee that blocked JDBC work will terminate; configure JDBC and driver/network timeouts.
This lifecycle protection does not make a `SqlSession` thread-safe. Do not use the same session
concurrently or commit a transaction while another thread is still using its JDBC resources.

== XML Configuration Support

You need to set ```quarkus.mybatis.xmlconfig.enable``` to ```true``` and set ```quarkus.mybatis.xmlconfig.path``` to the
mybatis xml configuration which the default value is ```mybatis-config.xml```.
The `quarkus.mybatis.environment` property selects the environment in the XML configuration file.
For the JTA behavior described in <<transactions>>, use `MANAGED` in that environment's
`transactionManager` element and enable JTA participation on its datasource.

[source, text]
----
# H2
quarkus.datasource.h2.db-kind=h2
quarkus.datasource.h2.username=sa
quarkus.datasource.h2.password=sa
quarkus.datasource.h2.jdbc.url=jdbc:h2:tcp://localhost/mem:default
quarkus.datasource.h2.jdbc.transactions=enabled

# MyBatis
quarkus.mybatis.xmlconfig.enable=true
quarkus.mybatis.xmlconfig.path=mybatis-config.xml
quarkus.mybatis.environment=development
quarkus.mybatis.h2.initial-sql=insert-h2.sql
----

[source, xml]
----
<!DOCTYPE configuration
        PUBLIC "-//mybatis.org//DTD Config 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-config.dtd">

<configuration>
    <typeHandlers>
        <package name="io.quarkiverse.it.mybatis"/>
    </typeHandlers>

    <!-- setup environment with Quarkus data source -->
    <environments default="development">
        <environment id="development">
            <transactionManager type="MANAGED"/>
            <dataSource type="QUARKUS">
                <property name="db" value="h2"/>
            </dataSource>
        </environment>
    </environments>

    <mappers>
        <package name="io.quarkiverse.it.mybatis"/>
    </mappers>
</configuration>
----

The dataSource type must be ```QUARKUS``` and the property ```db``` could be specified to the datasource name in the
quarkus configuration.

=== Type handlers and CDI

MyBatis creates and registers type handlers. The extension exposes registered handlers annotated with
`@MappedTypes` or `@MappedJdbcTypes` as CDI `@Singleton` beans, without client proxies that XML
`<typeHandlers><package .../></typeHandlers>` scanning could otherwise discover. This applies to
both JVM and native deployments.

Exposing these MyBatis-owned instances through CDI does not apply CDI field injection or interceptors
such as `@Transactional`. Avoid also declaring the handler classes as CDI managed beans, for example
by adding `@ApplicationScoped` or `@Singleton` to them. Independently discovered beans can cause
ambiguous injection or generate handler proxies and subclasses that XML package scanning does not exclude.
